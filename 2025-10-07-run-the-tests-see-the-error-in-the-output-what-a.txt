● The Error

  The test in test/order/order.e2e-spec.ts:114 is failing because:
  - Expected: totalAmount = 30.5
  - Received: totalAmount = 27.45 (which is 30.5 × 0.9, a 10% discount)

  Root Cause

  The global fixtures create 4 orders for the first customer (fixtures.getCustomers()[0]) dated 10, 15, 20, and 25 days ago. When the order test runs:

  1. Line 98: Uses fixtures.getCustomers()[0] (John Doe - the same customer with 4 historical orders)
  2. Line 79-82: OrderService.create() calls loyaltyService.calculateNextOrderAmount()
  3. LoyaltyService checks orders in the last month and finds >3 orders, applying a 10% discount
  4. The test expects 30.5 but receives 27.45

  This is a classic test interdependence issue - the global fixtures cause side effects that break tests expecting clean state.

  Possible Solutions

  1. Isolated Test Fixtures (Recommended)

  Each test file creates its own fixtures instead of sharing global ones.

  Pros:
  - Tests are completely independent
  - Tests can run in any order
  - Easy to understand test data scope
  - No hidden dependencies

  Cons:
  - Slightly more code duplication
  - Slower execution (more DB setup per test file)

  2. Per-Test Database Transactions

  Wrap each test in a transaction that rolls back after completion.

  Pros:
  - Fast test execution
  - Complete isolation between tests
  - No need to manually clear data

  Cons:
  - Requires test infrastructure setup (transaction management)
  - Can hide real-world issues with transactions

  3. Factory Functions Instead of Shared State

  Replace global fixtures with factory functions that create fresh data on demand.

  Pros:
  - Tests request only the data they need
  - No shared mutable state
  - Easy to create variations for specific test cases

  Cons:
  - Tests need to explicitly create all data
  - Slightly more verbose

  4. Fix This Specific Test (Quick Fix, Not Recommended)

  Use a different customer without historical orders or expect the discounted amount.

  Pros:
  - Minimal changes to fix this one test

  Cons:
  - Doesn't solve the underlying problem
  - Tests remain fragile and order-dependent
  - Will break again with new features

  5. Namespace/Partition Test Data

  Each test suite uses different customers/data to avoid collision.

  Pros:
  - Faster than isolated fixtures
  - Can still share some common data

  Cons:
  - Requires careful coordination
  - Still has some interdependence
  - Harder to maintain as tests grow
