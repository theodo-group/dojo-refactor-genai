  🔍 Root Cause Analysis (5 Whys)

  Why 1: Why does the test fail?
  → The test expects totalAmount to be 30.5, but receives 27.45

  Why 2: Why is the totalAmount 27.45 instead of 30.5?
  → A 10% loyalty discount is being applied (30.5 × 0.9 = 27.45)

  Why 3: Why is the loyalty discount being applied?
  → The OrderService.create() always calls loyaltyService.calculateNextOrderAmount() (order.service.ts:79-82), and the customer has >3 orders in the last month

  Why 4: Why does the customer have >3 orders in the last month?
  → The GlobalFixtures creates 4 orders for customers[0] (John Doe), all dated within the last 25 days (global-fixtures.ts:147-180)

  Why 5: Why are the test fixtures set up to make the customer loyalty-eligible?
  → Line 132 reveals: "// Create dates for the orders - to make first customer eligible for loyalty program". The fixtures were intentionally designed to test loyalty functionality.

  🎯 ROOT CAUSE

  Tight coupling through shared global state

  The GlobalFixtures creates a customer with 4 recent orders specifically to test the loyalty program. However, this same fixture data is reused across ALL tests. When
  order.e2e-spec.ts creates a new order using customers[0], the loyalty discount is automatically applied due to pre-existing orders, even though the order test shouldn't depend on
  loyalty functionality.

  The fundamental issues are:
  1. Shared mutable state: All tests share the same GlobalFixtures
  2. Hidden dependencies: Order tests have implicit dependencies on loyalty service behavior and customer order history
  3. Lack of test isolation: Test behavior changes based on fixture data created for unrelated features

  💡 Proposed Solutions

  Option 1: Test Isolation (RECOMMENDED)

  Address the root cause by isolating test data
  - Create test-specific fixture methods (e.g., createCustomerWithoutOrderHistory())
  - Or use a different customer (customers[1] or customers[2]) who doesn't have loyalty eligibility
  - Ensures tests are truly independent

  Option 2: Explicit Test Expectations

  Make the test aware of loyalty behavior
  - Calculate the expected amount dynamically based on the customer's loyalty status
  - More realistic but makes the test more complex

  Option 3: Mock LoyaltyService (Not Recommended for E2E)

  - Mock the loyalty service in order tests
  - Goes against E2E testing principles

  I recommend Option 1 - specifically using a customer without order history (customers[1] or customers[2]) in the order creation test. This is the simplest fix that maintains test
  isolation.

⏺ Excellent question! Looking at the code, I can see this is a systemic architectural problem affecting all test suites. Let me analyze the full scope:

  🔍 Systemic Problems Identified

  1. All 5 test suites share GlobalFixtures
  2. Tests mutate shared state:
    - customer.e2e-spec.ts deletes customers[1] (line 129)
    - product.e2e-spec.ts deletes products[1] (line 126)
    - loyalty.e2e-spec.ts even has a comment "This will cause issues in other tests" (line 65-66) and deliberately modifies fixture data!
  3. Fixtures loaded once per suite (beforeAll) not per test
  4. Hidden cross-feature dependencies: Order behavior now depends on Loyalty service, Customer deletion affects Order tests, etc.

  🎯 Systemic Solutions

  Option A: Factory/Builder Pattern (RECOMMENDED)

  Create reusable factory functions to let each test build its own isolated data.

  Advantages:
  - ✅ Complete test isolation
  - ✅ Tests are self-documenting (you see what data they need)
  - ✅ New features can't break existing tests
  - ✅ No hidden dependencies

  Structure:
  test/
  ├── factories/
  │   ├── customer.factory.ts    # createCustomer(), createCustomerWithOrders()
  │   ├── product.factory.ts     # createProduct(), createProducts()
  │   ├── order.factory.ts       # createOrder(), createOrderForCustomer()
  │   └── index.ts              # Export all factories
  └── [test-files].e2e-spec.ts  # Use factories instead of GlobalFixtures

  Example usage:
  it('POST / should create order without loyalty discount', async () => {
    // Each test creates only what it needs
    const customer = await createCustomer(app); // No order history
    const products = await createProducts(app, 2);

    const order = await createOrder(app, {
      customerId: customer.id,
      productIds: products.map(p => p.id),
      totalAmount: 30.5
    });

    expect(order.totalAmount).toBe(30.5); // No discount applied
  });

  Option B: Per-Test Fixture Reset

  Keep GlobalFixtures but reload data before each test (beforeEach)

  Advantages:
  - ✅ Simpler migration (keep existing fixtures)
  - ✅ Tests can't affect each other

  Disadvantages:
  - ❌ Slower (reloads all data for every test)
  - ❌ Still has hidden dependencies
  - ❌ Can't customize fixtures per test

  Option C: Minimal Fixtures + Factories (HYBRID)

  Create minimal base fixtures + factories for test-specific data

  Advantages:
  - ✅ Fast (minimal base data)
  - ✅ Flexible (factories for specific needs)
  - ✅ Good balance

  ---
  📋 Recommended Implementation Plan

  I recommend Option A (Factory Pattern) because it:
  1. Prevents this issue forever: Tests create their own data
  2. Makes tests readable: You see exactly what data each test needs
  3. Eliminates hidden dependencies: Each test is independent
  4. Scales well: New features don't break old tests
